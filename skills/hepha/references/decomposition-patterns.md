# 拆解模式

## 垂直切片

优先按用户价值路径拆分。例如“新增资料编辑”：

```text
SPEC-001/SC-001 查看资料 -> TASK-001 查询与展示
SPEC-001/SC-002 编辑资料 -> TASK-002 编辑与保存
SPEC-001/SC-003 保存失败 -> TASK-003 错误处理与恢复
```

每个任务同时包含必要的 UI、API 和数据改动，避免形成长期不可用的水平层。

## 风险前置

鉴权、支付、数据迁移和外部 API 先建立可执行探针或契约测试，再进入主实现。研究结论写入 decision-log，可复用结论提炼为 decision 或 troubleshooting 资产。

## 缺陷修复

```text
复现失败测试 -> 最小修复 -> 回归测试 -> 根因资产候选
```

验收条件描述修复后的用户行为，不写“修改某文件”。

## UI 交互

将可访问性、加载态、成功态、错误态和关键交互拆成场景。组件测试提供快速反馈，浏览器验证提供用户视角证据。

## 外部集成

按契约、认证、核心调用、错误/限流、展示路径拆分。不要把所有端点堆进一个任务。

## 反模式

- 按文件名拆任务。
- 先实现全部功能，最后单独补测试。
- acceptance 使用“完成”“正常工作”等不可执行描述。
- 所有 Summary 无差别发布成个人 Wiki。
- 将失败尝试当作已验证工程模式。
