## Spec

在写代码前固定用户可观察行为。Spec 必须包含目标、非目标、约束、场景和完成条件。场景使用稳定 ID，任务和测试引用该 ID。

不要把实现方案写成验收结果。例如，“使用 Redis”是方案，“并发请求只创建一份缓存值”才是行为。

## TDD

执行以下不可颠倒的顺序：

1. 写一个最小测试表达一个行为。
2. 执行测试，确认因目标行为缺失而失败。
3. 记录 RED 命令、退出码和关键输出。
4. 写最小实现。
5. 执行相同测试并记录 GREEN。
6. 重构后执行相关回归集并记录 regression。

测试因语法错误、环境缺失或错误断言而失败，不算有效 RED。

## 角色隔离

Orchestrator 持有任务图和状态机。Implementer 只接收当前任务上下文。Spec reviewer 只判断是否满足规格。Code reviewer 只判断工程质量。

可用子代理时，使用新鲜上下文：

- Implementer 输入：Spec、任务、允许文件、测试命令、项目约束。
- Spec reviewer 输入：Spec、验收、diff、测试证据。
- Code reviewer 输入：diff、相关源码、测试、风险。

不可用子代理时，在同一 Agent 内清晰分隔三个阶段，不在审查阶段为自己的实现辩护。

## 审查协议

Spec review 逐个输出场景结论：`pass | fail | missing-evidence`。

Code review 按优先级输出：

- P0：会造成数据、安全或核心功能严重错误。
- P1：正常路径可触发的正确性问题。
- P2：维护性、测试质量或边界问题。

存在 P0/P1 时回到 `doing`，修复后重新运行相关测试和两类审查。

## 例外

纯文档、格式化、静态资产等非行为任务可设置 `behavior_change: false`。仍需声明确定性的替代验证，例如链接检查、渲染检查或文件哈希。不要把“时间不足”作为跳过测试的理由。
